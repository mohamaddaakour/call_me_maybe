Chapter III
Introduction
III.1 What is Function Calling?
Large Language Models (LLMs) are powerful at understanding and generating human
language, but they don’t naturally produce structured, machine-executable output. Func-
tion calling bridges this gap by translating natural language requests into precise function
calls with typed arguments.
Consider this example: Natural Language to Function Call
User: "What is the sum of 40 and 2?"
Traditional LLM: "The sum of 40 and 2 is 42."
Function Calling System:
{
"function": "add_numbers",
"arguments": {"a": 40, "b": 2}
}
The function calling system doesn’t answer the question directly. Instead, it provides the
tools to solve it: the right function name and the correct arguments with proper types.

III.2 Why is This Important?
Function calling enables LLMs to:
• Interact with external systems: Call APIs, query databases, control devices
• Execute code: Perform calculations, data transformations, file operations
• Chain operations: Break complex tasks into executable steps
• Provide structured output: Generate JSON, XML, or other machine-readable
formats
• Extract structured data from unstructured text: For example, given a large
book, extract fields such as {protagonist name, protagonist sex, protagonist
age}
This technology powers modern AI assistants, code generation tools, and autonomous
agents, while also enabling tasks like automatic information extraction and knowledge
structuring from raw text.
III.3 The Challenge
Small language models (like the 0.6B parameter model you’ll use) are notoriously unre-
liable at generating structured output. When prompted to produce JSON, they might
succeed only 30% of the time. Yet production systems achieve 99%+ reliability with
these same small models.
How? The answer lies in constrained decoding — a technique that guides the model’s
output token-by-token to guarantee valid structure, without relying on prompting alone.

V.3 LLM Interaction
V.3.1 The LLM SDK
Attached to this project, you’ll find a wrapper class Small_LLM_Model in the llm_sdk
package that you can use to interact with the LLM.
The SDK provides several essential methods:
• get_logits_from_input_ids(input_ids: List[int]) -> List[float]
Takes a list of token IDs and returns the logits produced by the LLM model.
• get_path_to_vocab_file() -> str
Returns the path to the vocabulary file containing the correspondence between
token IDs and tokens.
• encode(text: str) -> Tensor
Encodes a text string into a tensor of token IDs using the model’s tokenizer.
• decode(token_ids: List[int]) -> str (optional)
Optionally decodes a list of token IDs back into a text string.
V.3.2 The Generation Pipeline
The LLM generation process follows these steps:
1. Prompt: Your natural language question
Example: "What is the sum of 2 and 3?"
2. Tokenization: The text is broken into subword units (tokens). Unlike simple word
splitting, tokenizers often include leading spaces, handle punctuation, and split
words into smaller components using algorithms such as BPE or SentencePiece.
Example (realistic): ["What", "˙Gis", "˙Gthe", "˙Gsum", "˙Gof", "˙G2", "˙Gand", "˙G3", "?"]
Note: The symbol "˙G", indicates a preceding space; real tokenizers preserve such
details to reconstruct text accurately.
3. Input IDs: Tokens are converted to numerical IDs the model understands.
Example (illustrative): [892, 318, 262, 4771, 286, 16, 290, 17, 30]
4. LLM Processing: The model processes these numbers through its neural network.
5. Logits: The model outputs probability scores for each possible next token.
Example: token_5: 0.001, token_42: 0.85, token_100: 0.02, ...
6. Token Selection: The next token is chosen based on these probabilities, usually
the one with the highest score.
At this stage, techniques like constrained decoding can be applied to restrict the
token choices and ensure outputs follow a specific structure, such as generating
100% valid JSON.

Important: This process repeats token-by-token. Each generated token is added to the
prompt, and steps 2-6 repeat until the complete response is generated.
Simplified view:
Prompt -> Tokenization -> Input IDs -> LLM -> Logits -> Next Token Selection
V.3.3 Understanding Constrained Decoding
Language models generate text one token at a time. At each step, the model produces
a probability distribution (logits) over all possible next tokens. Normally, you would
sample from this distribution or pick the highest probability token.
Constrained decoding intervenes in this process by modifying the logits before token
selection:
1. The model produces logits for all possible tokens.
2. You identify which tokens would maintain both a valid JSON structure and com-
pliance with the expected schema.
3. You set logits for invalid tokens (those breaking the schema or structure) to negative
infinity.
4. You sample only from the remaining valid tokens.
In this project, constrained decoding must not only ensure syntactically valid JSON
but also enforce a specific schema. For instance, if a field is constrained to a number
in functions_definition.json, the decoder restricts token selection to values satisfying
either an integer or a float, preserving both JSON validity and schema compliance. This
guarantees that every generated token maintains both structural and semantic validity,
enforcing the required schema. As a result, the produced JSON is 100% retrievable and
can always be parsed without errors.
Your solution must NOT rely on the model spontaneously producing
correct JSON from a prompt. Prompting the model with function
definitions and hoping for structured output is not reliable, and
it is not the skill we expect you to develop here.
Think about how you can use the vocabulary JSON file to map between
tokens and their string representations. This is crucial for
determining which tokens are valid at each generation step.

## Phase 3 - End-to-End Constrained Function Selection

Deliver the first non-empty end-to-end program for function definitions with no
parameters, then make function selection general.

Implementation work:

- Define a small generation-state machine for the exact output object structure. At
  this phase it must generate `{"name": <allowed-name>, "parameters": {}}` or an
  equivalent internal object that is validated before the final result is written.
- Represent the set of function names as a token-aware prefix trie or equivalent
  finite-state constraint. A token is allowed only when appending its decoded text
  remains a prefix of at least one valid function name or completes one.
- At every generation step, obtain logits from the model, reject every token that
  violates the current state, and greedily select the highest remaining logit. The
  function must therefore be selected by the LLM among structurally allowed choices,
  not by keywords, string similarity, rules, or hardcoded prompt answers.
- Include delimiters, quotes, punctuation, and JSON termination in the state machine.
  Account for vocabulary tokens that contain more than one character and accept a
  token only when its entire decoded text is valid from the current state.
- Add termination and safety rules: an explicit accepting state, a maximum token
  count, detection of no valid next token, and a useful error when the supported
  function set cannot be represented with the available vocabulary.
- Validate the generated name against the loaded definitions and use the pydantic
  result model to add the original prompt. Write the final array with exactly the
  keys `prompt`, `name`, and `parameters`.
- Reject functions containing parameters with a clear temporary phase limitation.

Executable result:

For any supplied set of zero-parameter functions, the command processes every prompt
and writes parseable, schema-compliant output. Function choice is made from model
logits under a name constraint. Inputs requiring arguments fail cleanly rather than
creating partial or fabricated output.

Verification checkpoint:

- Test multiple zero-parameter functions whose names share prefixes.
- Assert that every selected function name belongs to the current definition file.
- Parse every output and assert that its keys are exactly the three required keys.
- Use prompts and function names different from the examples to expose hardcoding.

## Phase 4 - Constrained String Argument Extraction

Extend the same token-level decoder to functions whose parameters are strings.

Implementation work:

- Expand the generation state to emit parameter keys in a deterministic order taken
  from the chosen function definition. Require every parameter exactly once and
  prohibit unknown or duplicate keys.
- Implement a JSON string state that permits valid content while enforcing quoted
  JSON syntax. Correctly handle escaped quotation marks, reverse solidus characters,
  control-character escapes, empty strings, spaces, punctuation, and Unicode text.
- Decide validity incrementally from the complete text represented by a candidate
  vocabulary token. Do not assume one token equals one character.
- Use model logits to choose the string value. Syntax and schema constraints may
  limit the choices, but heuristic extraction from the original prompt must not
  replace LLM generation.
- Permit a closing quote only from a valid string state, then constrain commas,
  following parameter names, braces, and final termination according to the selected
  function's schema.
- Decode the completed structure with `json.loads`, validate it with the pydantic
  models, and reject output containing extra text.
- At this phase, support zero-parameter and string-only functions; report other
  parameter types as unsupported.

Executable result:

The program handles arbitrary function sets containing no parameters or string
parameters, processes a full prompt array, and writes exact valid results without
depending on the model to format JSON correctly.

Verification checkpoint:

- Test empty strings, names with spaces, embedded quotes, backslashes, newlines,
  punctuation, and non-ASCII characters.
- Test functions with one and several string parameters.
- Assert that omitting, duplicating, or adding a parameter is impossible in every
  decoder state.

## Phase 5 - General Mandatory Scalar Schema Decoding

Complete schema-constrained decoding for the parameter types supplied by the
mandatory tests.

Implementation work:

- Implement JSON number constraints, including optional minus sign, integer digits,
  optional fractional part, and optional exponent where supported. Prevent illegal
  forms such as a lone minus, leading-zero errors, an incomplete decimal, `NaN`, or
  infinity. Convert a `number` parameter to a JSON number, not a quoted string.
- Implement boolean constraints that allow exactly the JSON literals `true` and
  `false`. Add `null` only if the mandatory input schema explicitly declares a
  nullable value; never infer nullability.
- If mandatory evaluation definitions contain other simple JSON types, map each
  declared type to an explicit finite-state constraint. Reject an unknown type while
  loading definitions rather than weakening validation.
- Generalize object generation to any number and ordering of required parameters.
  Use a stable internal order for generation while preserving the exact parameter
  names and required types from the selected definition.
- Revalidate the completed call independently of the decoder: the name must exist,
  the parameter key set must match exactly, and each Python value must match its JSON
  schema type. Take care that Python `bool` is a subclass of `int` and must not pass
  number validation accidentally.
- Process every prompt independently and collect one result per input prompt in the
  same order. Do not hardcode the provided function names, values, or test prompts.

Executable result:

The application fulfills the core mandatory behavior for general function-definition
